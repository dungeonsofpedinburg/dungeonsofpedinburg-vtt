# React + TypeScript + Vite

This template provides a minimal setup to get React working in Vite with HMR and some Oxlint rules.

Currently, two official plugins are available:

- [@vitejs/plugin-react](https://github.com/vitejs/vite-plugin-react/blob/main/packages/plugin-react) uses [Oxc](https://oxc.rs)
- [@vitejs/plugin-react-swc](https://github.com/vitejs/vite-plugin-react/blob/main/packages/plugin-react-swc) uses [SWC](https://swc.rs/)

## React Compiler

The React Compiler is not enabled on this template because of its impact on dev & build performances. To add it, see [this documentation](https://react.dev/learn/react-compiler/installation).

## Expanding the Oxlint configuration

If you are developing a production application, we recommend enabling type-aware lint rules by installing `oxlint-tsgolint` and editing `.oxlintrc.json`:

```json
{
  "$schema": "./node_modules/oxlint/configuration_schema.json",
  "plugins": ["react", "typescript", "oxc"],
  "options": {
    "typeAware": true
  },
  "rules": {
    "react/rules-of-hooks": "error",
    "react/only-export-components": ["warn", { "allowConstantExport": true }]
  }
}
```

See the [Oxlint rules documentation](https://oxc.rs/docs/guide/usage/linter/rules) for the full list of rules and categories.

## Локальный запуск

```bash
npm install
npm run dev       # Vite (5173) + sync-сервер (5174) в одном окне
```

`npm run dev` поднимает всё, что нужно для работы: и интерфейс, и связь окон, и
сохранение файлов выпуска на диск. Исторический псевдоним `npm run dev:all`
делает то же самое, а `start_windows.bat` / `start_mac.command` просто вызывают
`npm run dev` — отдельных команд для загрузки картинок, музыки и видео не нужно.

* Мастер-панель — http://localhost:5173/master
* Экран для OBS — http://localhost:5173/screen (источник «Браузер»)
* Связь окон — локальный WebSocket-сервер на порту 5174 (`server/index.mjs`)

OBS Browser Source живёт в отдельном процессе CEF, поэтому окна связывает
WebSocket: сервер держит последний снапшот в памяти и отдаёт его тому, кто
подключился позже — например, только что перезагруженному источнику в OBS.

Второй транспорт — `BroadcastChannel` (`pedinburg-episode-sync`) для вкладок того
же браузера: `/screen`, открытый рядом вкладкой, получает снапшот в том же тике,
без круга через сервер и даже когда сервер не поднят. Оба транспорта везут один и
тот же JSON, поэтому экран применяет первый пришедший и игнорирует дубль
(`applyRemoteSnapshot`) — сцена не монтируется дважды на один клик Мастера.

Отправка синхронная: подписка на стор зовёт `flushSnapshot` без `debounce` и
`setTimeout`, то есть в том же тике, где Мастер нажал сцену, персонажа или карту
(раньше состояние ждало 30 мс, и клик выглядел «не сработавшим» — в смоуке замер
пути «клик → экран» теперь 15–20 мс вместе с сокетом).

Подложка `/screen` строго чёрная на всех уровнях: класс `screen-root` вешает на
`html` и `body` `background-color: #000000` (правило в `src/index.css`), контейнер
страницы и сцена идут на `bg-black`. Серая заглушка «сцена без картинки» осталась
только в панели Мастера: на проекторе пустая сцена — чистый чёрный прямоугольник.

### Letterbox: сцена всегда видна целиком

Сцена на `/screen` рендерится в **виртуальных 1440×1080 (строгое 4:3)** и
масштабируется целиком:

```
scale = min(windowWidth / 1440, windowHeight / 1080)
```

Блок 1440×1080 лежит в чёрной оболочке `w-screen h-screen flex items-center
justify-center overflow-hidden` и вписывается трансформом
(`transform: scale(...)`, `transformOrigin: center center`), масштаб
пересчитывается на `window.resize` (`src/lib/stage.ts`, `stageScale`). Поэтому на
**любом** мониторе — 1378×720, 1280×720, 1920×1080, 4K — кадр виден целиком:
на 1378×720 масштаб равен 0.667 (кадр 960×720, по высоте окна ровно), головы
персонажей, верхние границы карт и кубики не срезаются краем дисплея, а полосы
кадрирования (letterbox/pillarbox) монолитно чёрные. Раньше сцена растягивалась по
высоте окна, и на 720p её верх уходил за край экрана.

Отдельные команды, если нужен только один процесс:

```bash
npm run dev          # Vite + sync-сервер (то же, что dev:all)
npm run dev:all      # псевдоним предыдущей команды
npm run sync         # только sync-сервер
npm run preview      # собранная сборка + sync-сервер
```

### Адреса и флаги

* `http://localhost:5174/health` — состояние сервера: есть ли снапшот, кто подключён;
* `?sync=ws://192.168.1.5:5174` — адрес сервера вручную (если OBS на другой машине);
* `VITE_SYNC_URL=ws://10.0.0.7:5174` — адрес для собранной сборки;
* `?badge=always` / `?badge=off` — индикатор связи на /screen: показывать всегда или выключить
  (по умолчанию виден, пока связи нет, и гаснет через несколько секунд после подключения);
* `SYNC_PORT`, `SYNC_HOST`, `WEB_PORT` — переопределение портов и адреса прослушивания.

## Папка assets: папки выпусков и кэш вне Git

Корневая папка `assets/` разделена на две строгие зоны:

* **`assets/episodes/<slug>/`** — выпуск целиком: `episode.json` (или одноимённый
  `<slug>.json` рядом), подпапки `scenes/`, `characters/`, `items/`, `music/`,
  `soundpad/`, `videos/`. Сюда пишет **экспорт**: он выгружает встроенные
  картинки, музыку и видео прямо в папку своего выпуска, поэтому её можно целиком
  заархивировать и передать. `<slug>` — безопасный идентификатор из названия
  выпуска (`generateEpisodeSlug`: «Порт в тумане» → `port-v-tumane`), он же виден
  бейджем в шапке Мастер-панели.
* **`assets/cache/`** — временный кэш и наследие: сюда попадают только запросы
  выгрузки с коротким путём (`scenes/...`) и файлы старых черновиков. Папку можно
  стереть целиком — приложение создаст её заново, если такой запрос придёт.

Картинки предметов (4-я колонка «Предметы», `category: "item"`) едут в `items/`,
а не в `characters/`: папка выбирается по категории в `characterAssetFolder`
(`src/lib/export-episode.ts`).

В репозиторий не попадает ни то, ни другое: в `.gitignore` стоят
`assets/episodes/*` и `assets/cache/*` (пустые каталоги переживают клонирование
благодаря `.gitkeep`, гигабайты видео — нет). Системные ассеты проекта
(плейсхолдеры и раздача кубиков) лежат в `public/` и не затрагиваются.

Старые пути работают без сбоев: запрос `/assets/scenes/...` сервер ищет в кэше, а
запрос `/assets/cache/...` (черновик, собранный до изоляции выпусков) — сначала в
кэше, затем запасным поиском по папкам `assets/episodes/**`: сначала точное
совпадение `<выпуск>/<тот же путь>`, потом по имени файла. Если файла нет нигде,
запрос уходит дальше по стеку Vite (в dev это страница приложения, а не файл).

## Проверки проекта

```bash
npm run lint    # oxlint
npm run build   # tsc -b && vite build
npm run smoke   # смоук-тесты стора и хелперов (src/store/syncSmoke.ts) в Node
```

`npm run smoke` поднимает Vite в SSR-режиме и sync-сервер на свободном порту,
затем прогоняет проверки из `src/store/syncSmoke.ts`: стор выпуска, связка
мастера и `/screen` через сокеты (кэш состояния, presence, переподключение),
экспорт/импорт, slug выпуска, разделители сцен, саундтрек, геометрия сетки,
размер кубиков, кластеризация группового перемещения фишек, геометрия рамки
выделения и кадры прыжка по дуге (`src/lib/token-cluster.ts`,
`src/lib/token-motion.ts`), состояния сцен (`src/lib/background.ts`), раскладка
сцены на четверых и letterbox-масштаб `/screen` (`src/lib/stage.ts`), калибровка
кубиков (`diceWidthPx`, эталон подложки 1248×888), их подложка внутри сцены,
карточки карт в левой колонке и флаг карты местности (`isBackgroundBattlemap`).
Часть проверок читает исходники через
`?raw` (`index.css`, `App.tsx`, `ObsScreen.tsx`, `SceneStage.tsx`, `SceneViewport.tsx`,
`DiceOverlay.tsx`, панель сцен, вкладку карт, стор) — так под сторожем оказываются
стили `/screen`, разметка жестов, виртуальное разрешение сцены и подключение
тостов, которые через стор не выразить.
Вторая фаза (`scripts/smoke-assets.mjs`) поднимает настоящий
HTTP-сервер Vite и проверяет раздачу и выгрузку: кириллица, пробелы и «№» в пути,
имена в форме NFD (macOS), Range-запросы, папку предметов `items/`, запись ассетов
в `assets/episodes/<slug>/<папка>/`, запасной поиск старого пути `/assets/cache/...`
и отсечение выхода за папку, чужого slug и чужого расширения.

## Выпуск: JSON + папка выпуска

Файл выпуска (`episodeSlug.json`) весит десятки-сотни килобайт: в нём только
текст — заметки актов (`groupNotes`), музыка актов (`groupTracks`), координаты
токенов 15×6, поле `episodeSlug` и относительные пути к ассетам
(`/assets/episodes/port-v-tumane/scenes/forest.jpg`).
Base64 (`data:...`) в JSON не пишется никогда: картинки и музыка лежат отдельными
файлами в папке выпуска.

* **Экспорт** («Экспортировать выпуск») выгружает выбранные в панели картинки и
  треки через локальный сервер (`vite.config.ts`, плагин
  `pedinburg:serve-episode-assets`, POST `/__pedinburg/assets`) в папку выпуска
  `assets/episodes/<slug>/` и только потом собирает JSON. Имя файла — `id` + слаг
  названия (`/assets/episodes/port-v-tumane/scenes/bg-harbor-порт-в-тумане.jpg`),
  поэтому повторный экспорт перезаписывает те же файлы, а не копит копии.
  Предметы (`category: "item"`) уезжают в `items/`, персонажи — в `characters/`,
  видео-сцены — в `videos/` (они грузятся в папку выпуска сразу, ещё при
  добавлении сцены). Туда же выгружаются картинки **всех состояний персонажа**
  (`characters[].states[].avatarSrc|fullBodyPngSrc`) и музыка актов
  (`groupTracks`): в JSON уезжают только пути, Base64 не попадает в файл.
* **Передача**: Продюсер сжимает папку `assets/episodes/<slug>/` в `<slug>.zip` и
  отправляет Мастеру вместе с файлом `<slug>.json`. Мастер распаковывает архив в
  `assets/episodes/` и импортирует JSON — всё на месте, потому что папка, файл и
  пути внутри JSON называются одним slug. Диалог экспорта показывает эту памятку.
* **Импорт** берёт `episodeSlug` из файла (в старых файлах поля нет — slug
  выводится из названия выпуска), а пути приводит к виду `/assets/...` (буквы
  диска, `file://`, обратные слеши и домашние папки `/Users/...` уходят), имена из
  macOS переводит из NFD в NFC. Если локального сервера нет (сборка раздаётся
  статикой), встроенный Base64 из старого файла в JSON не вернётся — поле
  останется пустым, а причина попадёт в отчёт экспорта.
* **Импорт** приводит чужие пути к виду `/assets/...` (буквы диска, `file://`,
  обратные слеши и домашние папки `/Users/...` уходят), а имена из macOS
  переводит из NFD в NFC. Если локального сервера нет (сборка раздаётся
  статикой), встроенный Base64 из старого файла в JSON не вернётся — поле
  останется пустым, а причина попадёт в отчёт экспорта.

## Видео-сцены и плеер Мастера

Сценой может быть не только картинка, но и видео (`.mp4`, `.webm`): файл
выбирается там же, где картинка («+» в разделителе или двойной клик по сцене —
`accept="image/*,video/mp4,video/webm"`).

* Видео сразу выгружается в папку выпуска `assets/episodes/<slug>/videos`
  (`src/lib/video-file.ts` и эндпоинт
  `POST /__pedinburg/assets`), поэтому в снапшот для `/screen` уезжает короткий
  путь, а не десятки мегабайт Base64. Предел одного файла — **1 ГБ на тело
  запроса** (в JSON ассет едет в base64, это ещё +33 % к размеру), поэтому
  тяжёлые видео-фоны в 70–500 МБ загружаются без ограничений; что больше —
  сервер честно отвечает `413` с причиной.
* Тип сцены определяется по расширению (`isVideoSrc`), поэтому `SceneStage`
  рисует `<video autoPlay playsInline muted object-cover>` вместо `<img>` —
  одинаково в панели Мастера и на `/screen`. `muted` обязателен: фон не должен
  перебивать саундтрек.
* Внизу Viewport Мастера выезжает плеер: он спрятан, пока курсор вне сцены, и
  появляется при наведении (`group-hover`/`focus-within`). Внутри — пауза,
  скруббер с таймкодом `00:14 / 01:30` и кнопка повтора (`Repeat`, включённый
  цикл подсвечен `text-amber-400`). Перемотка работает благодаря Range-запросам
  (`206 Partial Content`) в раздаче `assets/`.
* **Управление общее на два окна:** пауза, повтор и перемотка лежат в сторе
  (`videoPlayback`) и уезжают на `/screen` снапшотом синхронизации, поэтому
  проектор останавливается вместе с превью. Оба окна применяют команды одним и
  тем же кодом в `SceneStage`; перемотка отправляется один раз — на отпускании
  ползунка (`seekId` — метка события).
* Флаг зацикливания хранится и в живом состоянии (для `/screen`), и в самой сцене
  (`Background.isLoop`, по умолчанию `true`), поэтому выбор Мастера переживает
  возврат на сцену и уезжает в файл выпуска.

## Множественное удаление

Для персонажей и сцен работает режим выделения: ПКМ по элементу →
**«Выделить несколько»**. В секции появляются чекбоксы и плашка «Выбрано: N» с
кнопками «Удалить выбранные» и «Отмена», клик по элементу переключает его
отметку, а `Delete`/`Backspace` удаляют выбранное (в полях ввода и в редакторе
заметок клавиши работают как обычно — см. `isTextEntryTarget`). Выход из
режима — `Escape`, «Отмена» или удаление.

Логика удаления живёт в сторе (`deleteBatchCharacters`, `deleteBatchBackgrounds`,
`deleteBatchTracks`, `deleteBatchSoundpadSlots`): персонажи уходят со сцены и с
карт вместе со своими токенами, сцены — с раскладкой токенов, а выпуск не может
остаться без сцен. Заметки и музыка привязаны к группам сцен (актам), поэтому
удаление сцен их не затрагивает. В узкой аудио-панели треки и звуки удаляются по
одному через контекстное меню — пачечные действия стора там не нужны.

## Заметки и музыка актов

Заметки мастера пишутся **на группу сцен (акт)**, а не на отдельную сцену: акт —
единица подготовки выпуска. Слева во вкладке «Описание сцен» — узкая колонка
актов (5% ширины окна, как и колонка карт рядом), справа — редактор заметки
выбранного акта: имя правится инлайн, текст уезжает в `groupNotes`
(`updateGroupNote`), рядом видно число сцен и привязанную музыку. Заметки попадают
в файл выпуска как `groupNotes`; файлы старого формата (`sceneNotes` по сценам)
при импорте переносятся на акты своих сцен.

Музыку акта привязывают прямо на разделителе в библиотеке слева: кнопка с иконкой
`Music` («+») открывает выбор аудиофайла, файл сразу уезжает в папку выпуска
(`assets/episodes/<slug>/music/`), а в стор ложится путь (`groupTracks`). ПКМ по
кнопке — «Заменить трек» / «Удалить трек»; когда у акта есть музыка, иконка
подсвечена `text-primary`, а название трека видно в тултипе.

Аудио-движок (`useSoundtrackPlayer` + `src/lib/group-track.ts`) ведёт музыку актов
по правилам:

* **внутри одного акта** трек не меняется и не перезапускается — переключение сцен
  музыку не трогает;
* **переход в другой акт с треком** — кроссфейд: старый затухает (~1.5 с), новый
  проявляется;
* **переход в акт без трека** — музыка предыдущего акта продолжает играть;
* **ручной трек из правой панели** перекрывает музыку акта: она запоминает свою
  позицию и ставится на паузу, а на паузе ручного трека возвращается ровно с того
  же места (`savedCurrentTime`) и плавно нарастает.

Решения движка вынесены в чистые функции `resolveGroupTrackAction` и
`shouldResumeGroupTrack` — их проверяет смоук-прогон, а сам хук только исполняет
решение (в Node нет ни браузера, ни `HTMLAudioElement`).

## Состояния персонажей

У персонажа может быть несколько вариантов внешнего вида: «Обычное», «Раненый»,
«В ярости» и любые другие. У каждого варианта свои картинки — токен для карты и
иллюстрация для сцены, поэтому смена состояния мгновенно меняет и фишку на карте,
и выезжающую фигуру во Viewport и на `/screen`.

* **Данные**: `Character.states[]` (`CharacterState`: `id`, `name`, `avatarSrc`,
  `fullBodyPngSrc`) и `Character.activeStateId`. Если `states` пуст или его нет,
  базовые `avatarSrc`/`fullBodyPngSrc` и есть состояние `default` с именем
  «Обычное» — так читаются файлы выпуска старого формата.
* **Хелперы** (`src/lib/character.ts`): `characterStates` (все варианты, «Обычное»
  первым), `getCharacterActiveState`, `characterAvatarSrc`, `characterFullBodySrc`.
* **Действия стора**: `addCharacterState` (новый вариант сразу становится
  активным, а «Обычное» материализуется в списке — чтобы было куда вернуться),
  `setActiveCharacterState`, `removeCharacterState` («Обычное» удалить нельзя).
  Замена картинок (`updateCharacterImage`) правит **активное** состояние, а не
  базовые поля.
* **Интерфейс**: ПКМ по персонажу в левом рельсе и по его токену на карте →
  «Состояние» (`ContextMenuSub`): список вариантов с галочкой у активного, ниже —
  «Добавить состояние...» и удаление активного варианта. Диалог
  `AddCharacterStateDialog` спрашивает название, токен и иллюстрацию; без
  выбранных картинок вариант остаётся с картинками «Обычного».
* **Синхронизация и экспорт**: смена состояния лежит в `characters[]` стора,
  поэтому уезжает на `/screen` очередным снапшотом без отдельного канала; при
  экспорте картинки всех вариантов выгружаются в папку выпуска
  (`characters[].states[].avatarSrc|fullBodyPngSrc` попадают в список ассетов).


## Фишки на карте: прыжок по дуге и групповое перемещение

Фишки живут отдельным слоем поверх клеток: позиция считается по номеру клетки, а
не по DOM-ячейке сетки, поэтому переезд анимируется. Анимация — Framer Motion:
у каждой фишки два слоя (`BattleMapToken` в `BattleMapGrid.tsx`).

1. **Координаты клетки** — внешний `motion.div`: `x`/`y` в процентах от размера
   самой фишки (100% = ровно одна клетка), `0.45 s`, `easeInOut`.
2. **Высота прыжка** — вложенный `motion.div` на `useAnimationControls`: в момент
   смены клетки проигрывает кадры `y: [0, -32, 0]`, `scale: [1, 1.25, 1]` и
   `filter: drop-shadow(...)` (2 → 20 px), приземление доводит ease `backOut`.
   Кадры и тайминги лежат в `src/lib/token-motion.ts` — это общий контракт панели
   Мастера и `/screen`.

На проекторе фишка едет по той же сетке: снапшот синхронизации приносит новые
координаты, и прыжок стартует одновременно с панелью. Первое появление фишки и
снапшоты без смены клетки анимацию не запускают — иначе при открытии `/screen`
все токены подпрыгивали бы разом.

Выделение группы (вкладка «Карты местности»):

* Протяжка ЛКМ по пустому месту поля рисует рамку `border-amber-400
  bg-amber-400/10`; в выделение попадают фишки, чьи **центры** внутри рамки.
* `Shift`/`Ctrl`+ЛКМ по фишке добавляет или убирает её из выделения. Снимают
  выделение `Esc`, кнопка «Снять» рядом со счётчиком, переключение карты и любой
  обычный клик по карте.
* Выделенные фишки подсвечены `ring-2 ring-amber-400 ring-offset-2
  ring-offset-background`, в шапке карты появляется бейдж «Выделено: N».
* Группа перемещается **только перетаскиванием** любой выделенной фишки: клик по
  клетке ничего не двигает, он снимает выделение (случайный щелчок по карте не
  разбросает фишки). Клетки считает `clusterTargetCells`
  (`src/lib/token-cluster.ts`): цель плюс её ближайшие свободные соседи по
  возрастанию евклидова расстояния; клетки, занятые чужими токенами,
  пропускаются — в одну клетку фишки не встают. Позиции применяет
  `moveMultipleTokens` одним обновлением стора, поэтому на `/screen` уезжает один
  снапшот и вся группа прыгает по дуге одновременно.

## Состояния сцен и кроссфейды

У сцены может быть несколько вариантов кадра — «Ночь», «Пожар», «Разрушенная».
Механика повторяет состояния персонажей, чтобы Мастеру не приходилось учить две
разные схемы.

* **Данные**: `Background.states[]` (`BackgroundState`: `id`, `name`, `src`,
  необязательный `isBattlemap`) и `Background.activeStateId`. Состояний нет —
  значит «Обычным» считается базовый `src` сцены: файлы выпуска старого формата
  читаются как раньше.
* **Хелперы** (`src/lib/background.ts`): `backgroundStates` («Обычное» первым),
  `getBackgroundActiveState`, `backgroundStateSrc` (кадр для эфира),
  `isBackgroundBattlemap` (состояние может включать сетку карты).
* **Действия стора**: `addBackgroundState` (вариант сразу становится активным,
  «Обычное» материализуется в списке), `setActiveBackgroundState`,
  `removeBackgroundState` («Обычное» удалить нельзя). Замена картинки
  (`updateBackgroundImage`) правит **активное** состояние.
* **Интерфейс**: ПКМ по сцене в библиотеке → «Состояние»: список вариантов с
  галочкой у активного, «Добавить состояние...» и удаление активного. Диалог
  `AddBackgroundStateDialog` спрашивает название, файл (картинка или видео) и
  галочку «карта местности»; миниатюра сцены показывает кадр активного состояния.
* **Экспорт/импорт**: `backgrounds[].states[].src` входит в список ассетов
  (`episodeAssetFields`), чистится при экспорте, выгружается в
  `assets/episodes/<slug>/scenes/` и нормализуется при импорте — Base64 в файл
  выпуска не попадает.

### Кроссфейд при смене состояния

Смена состояния не мигает: прежний кадр ещё растворяется поверх нового
(`CROSSFADE_MS = 350` мс, `CrossfadeImage`).

* **Сцена** (`SceneStage`/`SceneLayer`): при смене `activeStateId` новый кадр
  проявляется, старый (картинка или видео) затухает поверх него. Ключ слоя — id
  сцены, поэтому переключение «Обычное» → «Ночь» происходит внутри слоя, без
  пересоздания и чёрной вспышки.
* **Персонаж на сцене**: иллюстрация активного состояния меняется тем же
  приёмом — прежняя поза растворяется за 350 мс, фигура не прыгает и не мигает.

## Сцена: до четырёх персонажей сразу

`activeCharacterIds` (массив до четырёх id) заменил одиночное поле: клик по
фишке в рельсе выводит персонажа на сцену, повторный — убирает. Пятый не
пускается, и об этом сообщает тост «Максимум 4 персонажа на сцене». Клик по
превью во Viewport очищает сцену целиком.

* **Раскладка** (`src/lib/stage.ts`): фигуры равномерно расходятся от центра —
  1 → 50 %, 2 → 35/65 %, 3 → 25/50/75 %, 4 → 18/38/62/82 %. Позиция каждой
  фигуры едет анимацией (`framer-motion`), поэтому при добавлении или уходе
  одного героя остальные плавно разъезжаются.
* **Размер фигур**: слот — квадрат высотой **80%** кадра (`aspect-square h-[80%]`,
  ширина по пропорции), картинка — `size-full object-contain object-bottom`
  (`pointer-events-none`). Ассеты персонажей обычно квадратные PNG, поэтому
  сторона слота равна высоте: фигура стоит на «полу» в полный рост. На 3–4 героях
  соседние слоты частично перекрываются — так и задумано, фигуры не мельчают.
  Слот лежит в слое на весь кадр (`absolute inset-0`), поэтому проценты считаются
  от высоты **сцены**: без этого высота не разрешалась и фигура вылезала в
  натуральном размере. Разъезд по горизонтали — `STAGE_RELAYOUT_MS` (350 мс),
  выезд снизу — `STAGE_SLIDE_MS`.
* **Вход и уход** играет `SceneStage`: список сравнивается с предыдущим кадром,
  поэтому анимация одинакова в панели Мастера и на `/screen` (туда список
  приезжает снапшотом `activeCharacterIds`; отдельных фаз в сторе больше нет).
  Вход — выезд снизу, уход — задвигание вниз, `STAGE_SLIDE_MS = 350` мс,
  `AnimatePresence initial={false}` (при открытии `/screen` никто не выезжает
  заново).
* **Резкость фигур** (`CrossfadeImage`): кадр несёт `animate-in fade-in`, но класс
  снимается сразу после проявления. Пока анимация «залита» (`fill-mode: both`),
  Chrome считает элемент анимируемым и держит его на отдельном слое композитинга,
  а такой слой растрируется один раз **до** масштабирования сцены (`/screen`
  растягивается до ×2 на 4K) — отсюда «мыло» на персонажах при резких декорациях
  (слои сцен лежат рядом, а не вокруг фигур). Без живой анимации кадр
  перерисовывается под масштаб; плюс на самой картинке `will-change: auto`,
  `transform: none` и `image-rendering: high-quality` — никакого `translateZ`,
  который как раз и промоутит слой. Выезд заканчивается целой позицией
  (`y: 0%` / `y: 100%`), поэтому на «полу» фигура стоит по пикселям, без мыла от
  дробного смещения.
* **Рельс**: все персонажи, стоящие на сцене, подсвечены золотой рамкой
  `ring-2 ring-amber-500`; последний вышедший остаётся «выбранным».

## Уведомления: тосты сверху по центру

Служебные сообщения больше не живут строками в панелях: их показывают тосты
[Sonner](https://sonner.emilkowal.ski/) — `<Toaster position="top-center" richColors />`
в корне приложения (`src/App.tsx`, обёртка `src/components/ui/sonner.tsx` с
тёмной темой). Тост исчезает сам (2–3 с), поэтому он не сдвигает панели и не
занимает место в левой колонке.

* Добавление и импорт сцен, треков, экспорт и импорт выпуска — `toast.success`;
  ошибки разбора и загрузки — `toast.error`; предупреждения о лимитах —
  `toast.warning` (например, пятый персонаж на сцене).
* Прогресс пакетных операций («Импорт сцен: 2 из 5») идёт в тот же тост по
  фиксированному `id`: сообщения заменяют друг друга, а не копятся столбиком.
* Из левой панели убраны технические строки (`Добавлено сцен: 1 из 1` и
  подсказки-статусы): их место заняли тосты, а сама панель стала компактнее.
  Памятка о том, как передать папку выпуска Мастеру, осталась диалогом: три шага
  с именами файлов читать в тосте неудобно.

## Кубики: геометрия и стабильность

* **Внутри сцены**: контейнер `#dice-box-overlay` — потомок `SceneStage`, поэтому
  канвас живёт в виртуальных 1440×1080 и масштабируется вместе со сценой
  (letterbox на `/screen`). Границы броска совпадают с границами подложки, и
  кубики не улетают за видимую область даже на 720p.
* **Подложка в пикселях канваса**: отступ подложки — `PLATE_INSET_PX = 96`
  (`5vw` считался от окна и «переезжал» на другом разрешении), отсюда эталон
  `DICE_REFERENCE_GEOMETRY = 1248×888`. Размер кубиков считается от фактической
  геометрии подложки: кубик всегда занимает 22…13 % её ширины
  (`diceScaleForCount` / `diceWidthPx`).
* **Замер — лейаутный**: `offsetWidth/offsetHeight`, а не
  `getBoundingClientRect()` — иначе CSS-масштаб сцены попадал бы в мир физики и
  кубики на 720p стали бы меньше задуманного.
* **Стабильность в долгой сессии**: инстанс один на страницу; после исчезновения
  плашки вызывается `clear()` (кубики и тела Ammo); потеря WebGL-контекста
  (`webglcontextlost`) пересобирает движок через `acquireDiceEngine`; зависшая
  физика отсекается сторожем `DICE_ROLL_WATCHDOG_MS` (7 с), броски идут строго по
  одному; `resizeWorld()` зовётся только при реальном изменении размера, поэтому
  слушатели `window.resize` в библиотеке не копятся.

## Превью сцены во Viewport Мастера

Кадр превью в левой колонке — компактный: по умолчанию **10% высоты экрана**
(`DEFAULT_VIEWPORT_HEIGHT_VH`) и пропорция **4:3** (`aspect-[4/3] w-auto`, центр —
`mx-auto`), внутри `SceneStage` на `size-full`. Так превью не съедает вертикаль у
рельса персонажей и библиотеки сцен, а фигуры считаются от высоты этого блока — в
маленьком Viewport они выглядят ровно так же, как на `/screen`.

Высота задаётся **ручкой на нижней границе тёмной подложки** (`data-viewport-resize`):
тянем вниз — превью растёт, вверх — сжимается, ширина пересчитывается по 4:3.
Пределы — 5–60 vh, шаг 0.1 vh; состояние локальное (в стор и снапшот не уходит),
поэтому `/screen` о высоте не знает. Жест — на PointerEvents с `setPointerCapture`
(работает и на тач-устройствах, и в CEF OBS), движение считается от
`window.innerHeight`, а не от `getBoundingClientRect()`: сцена на `/screen`
масштабируется через `transform`, и замер «поплыл» бы.

Плеер видео переехал из оверлея внутрь кадра в узкую полосу **под** ним
(`data-scene-player`): внутри самого превью контролы (ползунок и таймкод) шире
самой сцены и обрезались бы. Полоса занимает всю ширину колонки и видна только
тогда, когда в эфире видео-сцена.

## Чистый старт: пустой выпуск

Приложение (и кнопка «Создать новый выпуск») стартует с абсолютно пустым
выпуском: ни сцен, ни персонажей, ни треков, ни звуков, ни токенов —
`src/data/seed.ts` держит только пустые наборы и `backgroundIcon`, демо-данных
там нет. Активная сцена (`activeBackgroundId`) и карта (`activeMapId`) равны
`null`, поэтому сцена показывает подсказку «Сцена не выбрана», библиотека сцен —
«Выпуск пока пуст: сцен нет», а вкладка карт — «Нет карт местности». Пустой
выпуск корректно проходит экспорт и импорт: файл без сцен больше не считается
ошибкой.

## Вкладки Мастер-панели и глобальная аудио-панель

Главный экран занимает всю ширину окна: внешние поля слева и справа — ровно 1%
(`px-[1vw]`), а сам экран делится на три колонки (перетаскиваемые разделители).
Шапка живёт на тех же 1% за вычетом `0.625rem` с каждой стороны
(`pl-[calc(1vw-0.625rem)] pr-[calc(1vw-0.625rem)]`): это внутренние `px-2.5`
крайних элементов шапки — поля `<Input>` с названием выпуска и кнопки «Экран
OBS», поэтому видимый текст шапки и тела начинается на одной вертикали.

1. **Слева (35%)** — превью сцены, панель токенов и библиотека сцен.
2. **По центру (57%)** — вкладки: «Описание сцен» (1), «Карты местности» (2),
   «Кубики» (3). Клавиши `1`–`3` переключают вкладки. У каждой вкладки со списком
   (заметки актов, карты местности) левая колонка выбора занимает **5% ширины
   окна** (`w-[5vw]`), чтобы обе вкладки выглядели одинаково.
3. **Справа (8%, минимум 85 px)** — глобальная аудио-панель
   (`GlobalAudioSidebar`): она видна при любой вкладке, поэтому музыка и эффекты
   всегда под рукой. Панель стыкуется с центральной областью без лишней линии —
   её отделяет только разделитель колонок.

Карты местности: список карт — узкая колонка **внутри вкладки**, ровно 5% ширины
окна (`w-[5vw]`, `overflow-hidden`): карточки-миниатюры вписаны по ширине колонки
(100 %, 4:3), название лежит плашкой поверх нижнего края картинки
(`truncate bg-black/75`), поэтому длинный текст не ломает высоту, а список
аккуратно листается по вертикали. Активная карта подсвечена
`ring-2 ring-primary border-primary`. Справа — поле карты в пропорции эфира
(4:3, 1440×1080, 14 × 11 ровных клеток): под сеткой рисуется **арт активного
состояния карты** (`backgroundStateSrc`, картинка или видео), поверх — сетка
линий и токены, которые тащатся мышью. Раньше карты переключались горизонтальной
полосой сверху — её больше нет. Координаты токенов при импорте подрезаются до
сетки — файл с чужими координатами не оставит фишку за границами поля.

Важно про флаг карты: «Обычное» состояние сцены намеренно **не хранит** свой
`isBattlemap` — решает флаг самой сцены (`background.isBattlemap`). Иначе
материализованное «Обычное» замораживало старое значение, и сцена, которую позже
сделали картой, оставалась без сетки и токенов (та самая поломка «карты не
работают»). Свой флаг решает только у кастомных состояний — «Разрушенная» может
быть картой, а «Ночь» — нет.

Панель зажата по ширине: `min-w-0 overflow-hidden` у сайдбара (и у колонки
`ResizablePanel`) не дают квадратным плиткам распирать 8 % — лишнее обрезается
внутри плитки (`truncate`), а не растягивает колонку. Плитки идут в одну колонку
на всю ширину панели (`grid-cols-1`, `w-full aspect-square`), а высота делится
**70/30**: саундпад — `flex-[7]`, плейлист — `flex-[3]`, у каждого свой
`ScrollArea`, поэтому длинный список прокручивается внутри своей секции;
компактный транспорт внизу живёт вне дележа.

Аудио-панель состоит из двух секций одинаковых квадратных плиток и транспорта:

* **Звуки (саундпад):** плитка — иконка Lucide и название в одну строку
  (`truncate`), клик играет эффект, ПКМ → «Редактировать» / «Удалить»,
  «+» открывает диалог из набора `SOUNDPAD_ICON_NAMES` (`src/lib/soundpad.ts`).
  Эффекты играет `src/lib/sfx-player.ts`: у каждого звука свой `new Audio(src)`,
  он не трогает деки плеера и не глохнет вместе с музыкой.
* **Музыка (треки):** такие же квадратные плитки с обложкой (`coverSrc`) или
  иконкой `Music`, играющий трек подсвечен пульсирующей рамкой. Клик включает
  трек с кроссфейдом (повторный клик — пауза), «+» сразу открывает проводник и
  читает метаданные MP3, ПКМ → «Редактировать» / «Удалить», плитки
  перетаскиваются для сортировки плейлиста.
* **Транспорт внизу:** предыдущий/следующий трек, пуск-пауза, режим повтора,
  громкость и название текущего трека. Плеер живёт в `SoundtrackProvider` над
  панелями, поэтому переключение вкладок музыку не обрывает.

Слоты саундпада и треки входят в файл выпуска: при экспорте файлы ложатся в
`assets/episodes/<slug>/soundpad/` и `assets/episodes/<slug>/music/`, а в JSON
уезжает только путь. `/screen` ни музыку, ни эффекты не транслирует: звук
остаётся в панели Мастера.

## Релизы и версионирование

Версия проекта живёт в `package.json` (`"version"`) и совпадает с тегом
GitHub-релиза (`v0.1.0`). Нумерация — по SemVer: `MAJOR.MINOR.PATCH`.

* **PATCH** (`0.1.0 → 0.1.1`) — исправление багов, обратная совместимость
  сохранена.
* **MINOR** (`0.1.1 → 0.2.0`) — новая функциональность, старые файлы
  выпусков продолжают читаться.
* **MAJOR** (`0.2.0 → 1.0.0`) — несовместимые изменения (например,
  сломан формат `episode.json`).

**Обычный `git push` релиза не создаёт.** Релиз появляется только при
ручном запуске workflow `Create Release` (`.github/workflows/release.yml`)
— через веб-интерфейс GitHub (**Actions → Create Release → Run workflow**)
или через `gh workflow run release.yml -f version=X -f release_notes=...`.

**Пример первого релиза через GitHub CLI** (после `gh auth login`):

```bash
gh workflow run release.yml \
  -f version="0.1.0" \
  -f release_notes="- Первый публичный релиз.
- Пульт Мастера и экран OBS.
- Синхронизация через WebSocket."
```

**Старые релизы не удаляются.** Каждый релиз — отдельная страница со своим
архивом исходников, все они лежат в **Releases** от нового к старому.
Ссылка на последний стабильный релиз:
`https://github.com/<owner>/<repo>/releases/latest`.

Если новая версия ломается — откройте **Releases**, проскролльте до
предыдущего тега и скачайте его архив.
